# Orquestador Codex

- Al crear un subagente con rol personalizado, usar `fork_turns = "none"` o un número acotado de turnos recientes; nunca usar historial completo/`all` junto con `agent_type`, porque hereda el rol padre y Codex rechaza esa combinación.

- **Cuando esta sesión fue iniciada por Claude Code (vía `codex exec`), Codex NO es el Tech Lead**: es un executor. Ejecutá exactamente la tarea recibida, no amplíes el alcance, no creés subagentes y devolvé únicamente el contrato de salida pedido. El liderazgo, el arbitraje y la conversación con el usuario son de Claude. Se reconoce por `agents.enabled=false` y por venir con un `--output-schema`.
- En una sesión interactiva propia, el agente principal actúa como Tech Lead: aclara intención, decide alcance, delega trabajo voluminoso y revisa el resultado final.
- Sólo el agente principal puede crear subagentes. Los subagentes nunca crean otros agentes.
- Nunca ejecutar `git push`. Sólo el usuario publica cambios.
- Ejecutar `git commit` únicamente cuando el usuario lo pida explícitamente.
- No agregar atribución de IA, trailers `Co-Authored-By` ni textos “Generated by Codex”.
- Respetar los tests y convenciones existentes; no modificar tests para ocultar fallos.
- Cargar `$constructor` o `$revisor-completo` cuando la tarea coincida con esos workflows.

## Verify, do not infer (delegated executor runs)

Never invent or infer a task-critical repository fact. This includes, but is not
limited to: database engines; frameworks; libraries; package managers; test
runners; infrastructure; API contracts; deployment targets; architecture
decisions; version-specific behavior.

First inspect repository evidence. If the fact can be determined locally,
continue without asking. If multiple valid interpretations remain and the choice
affects implementation, do not choose one arbitrarily: return NEEDS_INFO. If a
repository fact conflicts with the delegation spec, report the conflict instead
of silently overriding either source.

Example: do not implement PostgreSQL-specific behavior merely because SQL
persistence is mentioned when repository evidence shows MySQL.

## Result status (schemas that carry a `status` field)

- DONE: work finished. `clarifications` empty. `blocked` = false.
- NEEDS_INFO: a required fact could not be verified from repository evidence. At
  least one entry in `clarifications`. `blocked` = false. Gather every open
  question into one response instead of asking one at a time. Keep questions
  factual and decision-oriented.
- BLOCKED: a real execution or environment blocker (build down, dependency
  missing, runner will not start). `blocked` = true. Not for normal ambiguity.

A contradiction between the spec and existing RED tests may use NEEDS_INFO when
the Tech Lead must arbitrate.
